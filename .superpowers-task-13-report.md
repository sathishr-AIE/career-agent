## API shapes

- `GET /api/memory` → `{"items": [MemoryItem, ...]}` where `MemoryItem` is
  `{id, label, answer, kind, options, is_volatile, last_confirmed_at,
  use_count, last_used_at, is_preference}`. `label` is `memory_key` for a
  keyed (preference) row, else `question_normalized` for a literal row —
  there is no raw/original-casing question text stored anywhere in
  `qa_bank`, only the normalized form, so that's what literal rows show.
- `PUT /api/memory/{id}` body `{answer: string, is_volatile: bool}` →
  `{ok: true, message}` / 422 `{ok:false, message:"The answer can't be
  empty"}` on a blank (trimmed) answer / 404 `{ok:false, message:"No such
  memory"}` on an unknown id.
- `DELETE /api/memory/{id}` → `{ok: true, message}` / 404 on unknown id.

## Twin-identification rule and its limits

Per the ledger ruling ("literal vs keyed drift"), a keyed row's literal
twins are the rows `qa_remember` wrote in the same call: same `answer` text
and same `source_job_id` (SQLite `IS` comparison so a `NULL`
`source_job_id` still matches `NULL`), with `memory_key IS NULL`. This
identification is used by all three of `qa_update`, `qa_delete`, and
`memory_list` (to hide twins from the list).

**Known limitation (matches what the ruling already accepts):** this is a
coincidence-based match, not a foreign key. A literal row from a
*different* job that happens to have the exact same answer text *and* the
same (or both-NULL) `source_job_id` would be wrongly treated as a twin —
hidden from `/memory`, and updated/deleted alongside the keyed row it
doesn't actually belong to. In practice `source_job_id` is job-specific for
every real caller (`ats.py`'s `_confirm_outcome`/ASK-answer path always
passes the live job's id), so a collision needs both the same job AND the
same literal answer text, which is narrow. The one path that still passes
`source_job_id=None` is `qa_upsert` (the pre-S4 caller, e.g. the
`needs_answer` origin branch in `answer_prompt`, left untouched per the
brief) — two `NULL`-job literal rows with identical answer text (e.g. two
unrelated questions both answered "Yes") could theoretically collide with
a keyed row that also has `source_job_id=NULL`, though `qa_remember`'s
production callers always pass a real job id, so this is a narrow edge.
