## JSON field for structured output, and how confirmed
`claude --help` documents `--json-schema <schema>` ("JSON Schema for
structured output validation"). The brief said to confirm the exact
top-level field name without making a live call. `claude --help` itself
doesn't name the field, so I grepped the installed `claude.exe` binary
(`C:\Users\FAI200-Sathish\.local\bin\claude.exe`) for the literal string
`structured_output` and found it used throughout the CLI's internal
message/attachment handling (e.g. `attachment.type==="structured_output"`,
`data:Gn.structured_output`) — confirming `structured_output` is the CLI's
real internal field name for parsed structured-output data, consistent
with the brief's own phrasing (`structured_output`/`result`). No `claude`
process was ever spawned to get this — `strings`-style `grep -a` on the
static binary only.

`_default_runner` parses accordingly: `data.get("structured_output")`,
falling back to `json.loads(data["result"])` if that key is absent (in
case an older CLI version doesn't add it and only returns the reply text
in `result`).

## Robustness implemented
- `route()` never raises: runner exceptions (including
  `subprocess.TimeoutExpired`) are caught and logged (`log.warning(...,
  exc_info=True)`), degrading to the fixed unknown-intent dict.
- `_coerce()` validates the runner's dict: non-dict, unknown `intent`,
  missing/non-string/empty `reply`, or non-string non-None `job_ref` all
  degrade to the same unknown dict.
- Input capped at 2000 chars before it reaches the runner (`text[:2000]`
  applied to the raw message, not the full prompt).
- `resolve_job`/`describe_matches` use parameterized SQL throughout;
  `%`/`_` in `job_ref` are escaped (`_escape_like` + `LIKE ... ESCAPE '\'`)
  so they're matched literally, not as SQL wildcards. Apostrophes are safe
  by construction (bound parameters, no string concatenation).
- `resolve_job` reuses `worker.QUEUE_WHERE` (imported from
  `career_agent.web.worker`, the single definition of "in the apply
  queue") for the substring-match path, so it can't drift from the real
  queue. The `#id`/bare-id path checks `job` directly (any status), per
  the brief.

## Concerns
- The `structured_output` field name is confirmed from the CLI binary's
  internal strings, not from a live invocation or first-party written
  docs — if a future CLI version renames it, `_default_runner`'s fallback
  to `result` (attempting `json.loads` on the reply text) would only
  succeed if the model happened to emit raw JSON as its text reply, which
  isn't guaranteed. Low risk (Task 20/S7 wiring should smoke-test one real
  call outside CI before relying on it), but worth flagging.
- `resolve_job`'s ambiguity rule (`len(matches) == 1`) reads through
  `describe_matches`'s 5-row cap; correctness for the 0/1/many
  distinction is unaffected by the cap (documented inline), but a caller
  wanting an exact ambiguous-count (not just ">1") would need a separate
  uncapped query — not needed by this task's interface.
