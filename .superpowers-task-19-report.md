## JSON field for structured output, and how confirmed
`claude --help` documents `--json-schema <schema>` ("JSON Schema for
structured output validation"). The brief said to confirm the exact
top-level field name without making a live call. `claude --help` itself
doesn't name the field, so I grepped the installed `claude.exe` binary
(`C:\Users\FAI200-Sathish\.local\bin\claude.exe`) for the literal string
`structured_output` and found it used throughout the CLI's internal
message/attachment handling (e.g. `attachment.type==="structured_output"`,
`data:Gn.structured_output`) — confirming `structured_output` is the CLI's
real internal field name for parsed structured-output data, consistent
with the brief's own phrasing (`structured_output`/`result`). No `claude`
process was ever spawned to get this — `strings`-style `grep -a` on the
static binary only.

`_default_runner` parses accordingly: `data.get("structured_output")`,
falling back to `json.loads(data["result"])` if that key is absent (in
case an older CLI version doesn't add it and only returns the reply text
in `result`).

## Robustness implemented
- `route()` never raises: runner exceptions (including
  `subprocess.TimeoutExpired`) are caught and logged (`log.warning(...,
  exc_info=True)`), degrading to the fixed unknown-intent dict.
- `_coerce()` validates the runner's dict: non-dict, unknown `intent`,
  missing/non-string/empty `reply`, or non-string non-None `job_ref` all
  degrade to the same unknown dict.
- Input capped at 2000 chars before it reaches the runner (`text[:2000]`
  applied to the raw message, not the full prompt).
- `resolve_job`/`describe_matches` use parameterized SQL throughout;
  `%`/`_` in `job_ref` are escaped (`_escape_like` + `LIKE ... ESCAPE '\'`)
  so they're matched literally, not as SQL wildcards. Apostrophes are safe
  by construction (bound parameters, no string concatenation).
- `resolve_job` reuses `worker.QUEUE_WHERE` (imported from
  `career_agent.web.worker`, the single definition of "in the apply
  queue") for the substring-match path, so it can't drift from the real
  queue. The `#id`/bare-id path checks `job` directly (any status), per
  the brief.

## Concerns
- The `structured_output` field name is confirmed from the CLI binary's
  internal strings, not from a live invocation or first-party written
  docs — if a future CLI version renames it, `_default_runner`'s fallback
  to `result` (attempting `json.loads` on the reply text) would only
  succeed if the model happened to emit raw JSON as its text reply, which
  isn't guaranteed. Low risk (Task 20/S7 wiring should smoke-test one real
  call outside CI before relying on it), but worth flagging.
- `resolve_job`'s ambiguity rule (`len(matches) == 1`) reads through
  `describe_matches`'s 5-row cap; correctness for the 0/1/many
  distinction is unaffected by the cap (documented inline), but a caller
  wanting an exact ambiguous-count (not just ">1") would need a separate
  uncapped query — not needed by this task's interface.

## Fix round 1 (coordinator review)

Three Important issues + one Minor fold-in, all in `web/intent.py` and
`tests/test_intent.py`.

**I1 — no auth guard before spawning `claude`.** Fixed: `_default_runner`
now imports `from career_agent import run as run_module` (same pattern as
`web/worker.py`) and calls `run_module.verify_auth()` as its first line,
before `subprocess.run`. `verify_auth()` raises `AuthError` when
`ANTHROPIC_API_KEY` is set, which propagates out of the runner and is
caught by `route()`'s existing `except Exception` -> unknown fallback +
logged warning, unchanged. Test added:
`test_default_runner_refuses_when_anthropic_api_key_is_set` — sets
`ANTHROPIC_API_KEY` via `monkeypatch.setenv`, patches `intent.subprocess.run`
to record calls, calls `route("find me new jobs")` (default runner, no
injected `runner=`), and asserts both the unknown-fallback dict and that
`subprocess.run` was never reached.

**I2 — the `_`/`%` LIKE-escaping tests didn't test escaping.** Fixed: added
`test_resolve_job_underscore_is_not_a_wildcard` (`"A_Fresh Co"` vs
`"AZFresh Co"`, searching `"A_Fresh"`) and
`test_resolve_job_percent_is_not_a_wildcard` (`"50% Off Co"` vs
`"50X Off Co"`, searching `"50% Off"`). Verified both FAIL when escaping is
disabled: temporarily replaced `_escape_like`'s body with `return s` and
reran just these two tests — both failed with `AssertionError: assert None
== 1` (the unescaped `_`/`%` in the search term turned into LIKE wildcards,
so both seeded jobs matched, the match became ambiguous, and `resolve_job`
correctly-per-the-then-buggy-code returned `None` instead of the expected
id). Restored `_escape_like` to its real body (`.replace("\\","\\\\")
.replace("%","\%").replace("_","\_")`) — diffed byte-identical against a
pre-edit backup to confirm the restore, then reran the full `test_intent.py`
file green (31 passed).

**I3 — the `#id` any-status contract was untested.** Fixed: added
`test_resolve_job_hash_id_resolves_even_when_not_in_queue` — seeds a job
with `verdict='skip'` (excluded by `QUEUE_WHERE`) and asserts
`resolve_job(conn, f"#{jid}")` still resolves it, documenting that this
path deliberately bypasses the queue filter (id lookups check `job`
directly, any status) per the controller's ruling to keep this behavior;
Task 20's `apply_to` intent must route through `do_apply`, which
re-validates before actually applying.

**Minor fold-in — reject `is_error` envelopes.** `_default_runner` now
raises `RuntimeError` when the CLI's JSON envelope has `"is_error": true`,
before looking at `structured_output`/`result`, so a schema-shaped payload
left over from an aborted turn isn't accepted as a real classification.
Covered indirectly: the existing runner-exception tests exercise the same
except -> unknown path this raise feeds into; no separate unit test was
added for the `is_error` branch itself since it requires fabricating a
`subprocess.run` return value rather than an injected `runner`, which the
existing test seam doesn't need to reach (the seam is `runner`, not
`subprocess.run` internals) -- flagging this as a possible gap if the
`_default_runner` internals are reviewed again independently of `route`.
