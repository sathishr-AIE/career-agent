## Fix round 1 (review: I1, I2, minor)

**I1 -- stale End date survives "currently work here".** Fixed both sides, as required:
- `Profile.tsx`: the `current` checkbox's `onChange` now also clears `end` (`end:
  e.target.checked ? '' : w.end`), not just `current`.
- `api_profile.py`: new `_clear_end_when_current(body)` runs on the stripped body before
  validation -- any work row with `current: true` gets `end` forced to `""` regardless of
  what was submitted, so a second client or a hand-built request can't reintroduce the bug.
- Test: `test_put_current_true_clears_a_stale_end_date` -- PUTs `current: true, end:
  "2023-01"`, asserts the reloaded file has `end == ""`.

**I2 -- blank rows validate and pollute prompts.** Fixed in `api_profile.py` only
(`config.py`/pydantic model untouched, as instructed):
- New `_reject_blank_rows(body)` runs after stripping/normalizing and before constructing
  `CandidateProfile`. A work row with a blank `company` or blank `title`, or an education
  row with a blank `institution`, adds a `{"work_history.<i>.<field>": "<Field> is
  required"}` / `{"education.<i>.institution": "Institution is required"}` entry. These
  errors **merge** with any pydantic `ValidationError` from the same request (`setdefault`,
  so a blank-row message wins over a pydantic one at the same path) rather than
  short-circuiting -- a request that's simultaneously missing a name and has a blank work
  row now reports both, matching `save_settings`' validate-everything-before-writing rule.
  This also fixed a regression the naive short-circuit version introduced: the pre-existing
  `test_put_invalid_returns_422_and_leaves_file_unchanged` test (blank name + missing
  company) stopped seeing `candidate_name` in `errors` until the merge was added.
- `Profile.tsx`: rows now carry a client-only `id` (see minor, below). Before PUT, work/edu
  rows where every field is still blank (`isBlankWork`/`isBlankEdu`) are dropped from the
  payload so an accidental "Add" + Save doesn't error; a row with even one field filled is
  sent as-is and shows its own per-field error inline if the backend rejects it.
- Tests: `test_put_partially_blank_work_row_returns_422_and_leaves_file_unchanged` (company
  blank, title present -> only the company key errors, file unchanged),
  `test_put_fully_blank_work_row_returns_422`, `test_put_blank_education_institution_returns_422`.

**Minor -- stable row ids.** `WorkRow`/`EduRow` (local types, `WorkEntry`/`EduEntry` +
`id: string`) replace the array index as the React `key` and as the basis for per-field
error lookup (`work:<id>:company` instead of `work_history.<i>.company`). `id` is generated
with `crypto.randomUUID()` (Math.random fallback) on load and on every "Add", and stripped
out of each row before it's sent (`{ id, ...rest }` -- exempt from `noUnusedLocals` as the
recognized object-rest-omit idiom, confirmed clean under `tsc -b`).

This mattered beyond tidiness once I2's blank-row filtering shipped: the backend's 422
errors are indexed against the *filtered* (sent) array, which can differ from
`profile.work_history`'s index whenever a blank row sits upstream of a row that errors.
`remapRowErrors()` walks the raw `{"work_history.<i>.field": msg}` response using the exact
`sentWork`/`sentEdu` arrays that were PUT, turns each into `work:<row.id>:field`, and the
form looks errors up by id -- so display stays correct regardless of what got dropped.
